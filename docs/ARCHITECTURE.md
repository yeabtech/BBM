# Dependency boundaries

Dependencies point inward: presentation and infrastructure may call application; application may call domain and its own ports; domain imports no project modules. The shared-contracts package carries only public transport shapes.

`npm run architecture:check` scans TypeScript import/export specifiers in server domain and application directories. It rejects infrastructure/framework imports in domain and framework/driver imports in application. This is a pragmatic guard, not a complete TypeScript dependency graph analyzer; aliases and dynamic imports are outside its coverage.

## Client boundaries

The client keeps Phaser bootstrap in `game/create-game.ts`, scene coordination in `game/scenes`, keyboard and touch adapters in `game/input`, and drawing in `game/rendering`. The `@bbm/game-simulation` workspace is a Phaser-free shared simulation kernel: it owns movement constants, platform/hazard/checkpoint/pickup geometry, deterministic movement and collision, and prediction/interpolation primitives. Physics revision `bbm-physics-v3` includes bounded circle contacts with low-speed restitution suppression and tangential friction, plus centralized object/effect settings. The single-player `/play` scene still uses Phaser Arcade Physics as its only physics owner. The multiplayer scene has no Arcade physics world; it predicts through the shared fixed-step functions and renders server snapshots. The root route hosts the lobby and networking adapter.

## Multiplayer lobby boundaries

Guest profiles and room membership are authoritative on the server. Guest tokens are returned once to the client, while PostgreSQL stores only SHA-256 token hashes. The client sends the token in the versioned WebSocket authentication message; tokens are never placed in URLs or room snapshots. Shared contracts define protocol v2 message shapes and runtime parsers.

The room domain owns capacity, host, readiness, presence, expiry, and closure rules. Application services coordinate those rules through repository and security ports. PostgreSQL adapters persist profiles, rooms, membership, and revisions; row locks serialize membership changes, and database constraints enforce one active room per guest and room membership capacity. An idle-room sweeper expires open rooms, host disconnects get a bounded grace period, and process startup closes any rooms left open by a prior process. The host can close a room by leaving; a non-host can leave without closing it. `prepare_to_start` only reports readiness and does not start a race.

HTTP and WebSocket transports validate origin, payload shape, and request limits. Production configuration requires HTTPS and trusted-proxy handling when TLS terminates upstream. In-memory IP rate limits are process-local and are intended as a basic abuse guard for this single-instance foundation, not a distributed rate-limiting system.

LAN hosting is opt-in through `LAN_ENABLED=true`; without it the API bind must remain loopback. LAN mode defaults to `0.0.0.0` and can be narrowed to an IP assigned to a local interface. `/api/lan-info` reports only whether LAN mode is enabled, the configured port, private IPv4 interface addresses, and whether this server serves the client bundle. The browser can select a host and port for both HTTP guest requests and the existing `/ws` connection. Origin checks, token-in-header/message authentication, room membership, and server-authoritative simulation remain unchanged. Discovery broadcasts are not used.

## Client hosting and origin policy

`CLIENT_DIST` optionally points at a built client bundle (`apps/client/dist`). When set, the existing HTTP server serves the Vite build and its HTML routes (`/`, `/play`, `/play.html`) on the same port as `/api` and `/ws`; `/api` and `/ws` are handled first, the bundle is confined to its directory, and unmatched paths return a plain 404 rather than the client page. The Vite build uses `base: "./"` so the same bundle works under a Vite dev URL or the API origin.

Origin validation lives in one module, `presentation/http/client-origin.ts`, shared by the Express app and the WebSocket gateway. An origin is accepted when it exactly matches `CLIENT_ORIGINS`, or (outside production) when it is an HTTP same-host Vite origin on ports 5173-5180, or when this server serves the client bundle and the origin's hostname equals the request `Host` hostname with a matching effective port (browser-defaulted `:80` included). Because the client page, API, and WebSocket share one origin in hotspot mode, no additional origin configuration is required, while unrelated sites remain rejected. Production keeps its explicit HTTPS origin list.

## Race lifecycle

Race sessions have a distinct domain entity and application service. `RaceRepository.startForHost` locks the room, revalidates its host connection and readiness, and persists the countdown in the same transaction. The room repository uses that room lock to reject new members during Countdown or InProgress. One shared injectable scheduler advances persisted deadlines, avoiding per-race timers and duplicate callbacks; the polling interval runs only while at least one race is active and is cleared on cancellation or shutdown. Countdown messages carry an absolute server deadline and server time; the browser estimates clock offset and renders from that shared timestamp. The official start is the countdown deadline, and the 120-second timeout is measured from it. Timeout cancels the race but leaves the room open for a new race session; room readiness remains separate. Host departure, room expiry, or host-grace expiry cancels an active race. A non-host disconnect does not cancel it, and reconnect receives the existing race snapshot. Startup recovery and graceful shutdown cancel active races with `ServerRestart` before room shutdown. No movement synchronization is part of this layer.

## Authoritative movement

`GameplayService` owns in-memory player states for each active race. It captures two or three participants when the countdown starts, assigns non-overlapping positions on the first platform, and simulates only after the persisted race enters `InProgress`. Two-player races complete after the first finisher; three-player races require all three finishers. Disconnect does not shrink this fixed participant set. One server monotonic clock and one shared race scheduler drive all sessions. The simulation accumulates time in fixed 1/60-second steps, runs at most eight catch-up steps per callback, drops excess accumulated time, and emits snapshots at 20 Hz. Race cancellation, timeout, room closure, and shutdown remove the corresponding runtime state; movement ticks are not written to PostgreSQL.

Protocol v2 movement frames carry only race ID, increasing sequence, horizontal direction, and jump-held intention. Authenticated socket identity supplies the guest ID. The server validates membership, input rate (120/second maximum), sequence gaps, bounded per-player queues, and server-receive freshness; stale/disconnected input becomes neutral after 250 ms. Snapshot messages include the same world dimensions/revision and authoritative states for all members. A client with excess socket buffered bytes has superseded movement snapshots dropped instead of blocking simulation. Local movement is predicted through the same shared step function, reconciled by input acknowledgement and replay of pending input segments; remote states use a bounded eight-snapshot interpolation buffer with 100 ms maximum extrapolation. The multiplayer Phaser scene does not create Arcade bodies or apply local gravity/collisions.

The server resolves player circles in stable slot order with bounded passes, mass-weighted positional correction, restitution only for approaching contacts, low-speed bounce suppression, tangential friction, and platform/world constraints. Grounded support transfers to balls above it, and moving support carries a resting ball horizontally. `GameplayService` owns one shared checkpoint, proximity-validated pickup inventory, active effects, server-timed respawn, finish timestamps, and result status. Finished or respawning players are excluded from collision/pickup processing as applicable. Final results are stored once per race in additive `race_results`; physics ticks remain in memory. A timeout preserves completed finish places and marks the remaining players unfinished or disconnected.

Phase 7 adds stable-ID obstacle definitions to the shared level and advances each race's moving platforms, falling-block lifecycle, and crusher paths on the same fixed simulation tick. Their current coordinates and states travel in validated gameplay snapshots, so reconnects receive the live environment. The multiplayer scene renders those snapshots and decorative scenery; decorative palette, parallax hills, clouds, and route labels live in `apps/client/src/game/level/level-visual-config.ts` and are not imported by server code. Spikes, falling blocks, crushers, and pits use the existing server-owned respawn rules.
